## 发现 1 / P1：回查验收绕过回执版本门——已修复

修复前位置：`openvela_smart_home/dashboard/bridge_server.py` 的 `lookup_http_request`。隔离复现：请求为 unknown；回查返回 applied、回执 `state_version_after=10`；当前快照仅 version=1，但目标数值碰巧相同。旧实现仍返回 `finished/task_complete=True`。

修复后回查与首次执行均要求有效整数回执版本，并且当前快照版本覆盖回执版本，之后才调用目标验收。旧版本或缺失版本保持 `observation_pending/task_complete=False`；新版本到达后可以仅查询完成。`goal_acceptance` 明确报告观测是否覆盖回执版本。

已检查修复后代码和对应先失败后通过的回归；本次独立执行请求恢复集合 10/10 通过。

## 发现 2 / P2：澄清动作提交后崩溃，合并目标无法恢复——已修复

修复前，原始请求账本只保存当轮“调到60%”；服务器合并的“把卧室灯光设为60%”仅在整个操作返回后进入结果。若动作已提交而进程在结果落库前停止，回查无法恢复房间和完整目标，永久停留在待验收。

修复后新增 `request_resolutions`，与原始请求哈希绑定。`process_command` 在规划前持久保存服务器合并命令，执行器在实际状态修改或 MQTT 提交前再保存经完整校验的目标合同。首次绑定后，房间、目标值、目标批次和能力范围不可更换；绑定耗时后重新检查 deadline。

调用身份通过 `ContextVar` 在进程内传递，`execute` 的 `finally` 还原 token；公开 context 不携带 journal 回调，也不能授予目标。并发回归确认两个线程不串请求 ID，退出后活动绑定为空。回查读取持久合同；旧记录仅回退到可信原始命令，不使用模型结果或回执动作反推用户目标。

离家场景的能力范围和 `security_arming` 未支持标记与目标同时持久保存。崩溃恢复后可以确认灯帘部分已达标，但整体 `task_complete/semantic_complete` 仍为 False。巡检恢复验证其真实温湿度读取目标。三轮澄清后崩溃、离家、巡检、不可变绑定、公开上下文及并发隔离均已进入独立运行的 10 项恢复回归。

## 发现 3 / P2：未送达请求可能永久封锁页面——已修复

修复前，POST 尚未到服务器便断网时，页面保存了 pending ID；恢复后回查得到 `not_found`，但每次新命令都只回查后返回。刷新继续恢复同一 pending，页面没有结束等待入口。

修复后提供显式“结束等待并保留记录”，旧 ID、原命令和状态留在会话历史，可继续 GET 回查；新意图另用新 ID。页面明确提醒旧请求仍可能执行，不会自动重发 unknown 动作。`clearPending(id)` 仅能清理对应 ID，旧响应迟到不能清除后来新请求。历史值渲染经过转义。

本次独立运行 `node --test docs/intrinsic_v5/test_dashboard_requests.cjs`，5/5 通过，包括未送达请求归档、重载后历史保留及旧响应与新 pending 竞态。

## 其余已核查的实现

- 明确请求目标与动作批次逐项、有序匹配；模型自报完成不能代替执行和验收。公开下划线字段剔除，服务器场景目标仅从内部边界授予。
- 请求账本在规划前绑定 ID 和完整公开请求；重复、冲突、processing、interrupted 各有确定行为。未知记录仅回查，不再次规划或提交。
- 正式启动使用总预算及首端预算。规划后、目标持久绑定后、回执 reservation 后与实际发布前均有截止时间保护；已提交动作的后续回执等待与迟到新提交分开处理。
- MQTT 断连清空 ready、唤醒等待者；恢复后重订阅，unknown 命令不会因重连自动重发。
- GET 状态立即返回带年龄/过期/未知的缓存，只允许单个后台刷新；当前目标验收仍使用严格同步快照，关闭流程取消并等待刷新。
- 持久模式持有 OS 级独占锁、校验 schema 和执行模式，启动对账不以历史回执覆盖软件实体当前状态。
- 排队、在途和分任务成本来自适配器实际计数与耗时；上游 GPU 队列、显存和实际无线链路未观测字段仍为 unknown。

## 补充复核：真实模型空计划后的恢复缺口

上述审查完成后，主控进行了真实本机模型烟测。`docs/intrinsic_v5/real_smoke_report.md` 保留了首次失败：Qwen2.5-1.5B 对“把客厅灯光设为35%，再把卧室灯光设为25%”返回空动作并要求指定亮度；原恢复器仅因调用 `ok=True` 就标记 `primary_success`，未调用备用。网关没有执行错误动作，`task_complete=False`。这是明确目标上的模型理解失败和恢复缺口，不是成功结果。

主控随后在 `planning_recovery.py` 新增受限的 `_resolved_request_without_plan`：仅当请求能由服务器完整目标语法解析、首端无动作/无语义完成/无结果错误且没有明确拒绝或澄清标记时，允许在剩余预算内尝试一次备用。模糊请求、未支持能力、明确 terminal 标记、HTTP 4xx、非空动作计划仍不走此新分支。该变更没有放宽白名单、原始请求目标合同或执行验收；恢复器本身只规划，不执行动作，也不能嵌套恢复器。备用同样返回空计划时仅记录 incomplete，不循环。

独立复核执行：新空计划回归与原恢复回归合跑 **33 passed、72 subtests passed**。另用虚拟时钟和记录型 planner 做了 **12 项独立边界探针**：6 类明确拒绝/澄清标记不启动备用；HTTP 400/403/422 不启动备用；首端空计划耗尽总期限后不启动备用；备用迟到时清空动作；首端非空部分计划不触发备用。均通过，未发现此补修绕过拒绝、过期保护或导致多次执行。

这些验证证明恢复控制流已修复，不能把首轮模型失败改写为成功，也不能据此声称 1.5B 模型理解能力或整体准确率已经提高。补修后的真实模型结果由主控另行记录。
