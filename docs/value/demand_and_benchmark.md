# 需求背景与可核验差异化

版本：2026-11-11；来源编号对应 `public_sources.json`。本页的需求方为待验证画像，没有具名企业背书。用户当前未提供可核实的使用经历，也未开展访谈或问卷；因此实际用户需求证据仍为 0 份。

## 需求链条

Home Assistant 官方已提供自然语言控制、完整本地语音链、云模型以及本地 Ollama 控制路径 [S1–S5]。这说明“家庭控制可选择不同处理位置”是现存技术路径。本地语音指南同时指出不同模型的指令范围、运行硬件与处理速度有取舍 [S2]；本地 LLM 集成也说明模型工具能力与小模型误操作的限制 [S3]。官方资料支持技术问题存在，不能推出住户普遍受此困扰、断网发生频率或客户愿付多少钱。

本作品提出一个可检验的服务连续性问题：同一家庭命令通过本地或远端模型规划时，WAN、LAN、模型服务和设备执行分别可能失败。若入口只知道“服务在线”，就难以解释是远端不可达、本地排队、输出被拒绝，还是设备未确认。需要保留不同能力的处理路径，并把失败和能力损失交给使用者或维护者理解。此问题可以先在隔离的 PC 模拟设备上验证，再由真实使用者判断是否值得部署。

| 利益相关者（假设画像） | 目前可描述的任务 | 需验证的业务影响 | 采证方式 |
|---|---|---|---|
| 住户/实际操作者 | 输入明确或复合命令，确认结果 | 是否在降级后仍能理解完成了什么、接下来如何操作 | 五分钟试用，记录复述和实际操作 |
| 智能家居集成服务商 | 配置本地设备、模型服务、维护入口 | 是否减少故障定位时间、增加硬件和维护负担 | 使用真实故障工单计时；目前无工单 |
| 部署维护者 | 检查模型/链路/动作事件 | 是否能用日志找到故障层并重放 | 盲测故障归因、重放相同事件 |
| 设备/家庭授权人 | 决定允许接入的设备与动作 | 授权设置是否明确、拒绝是否符合预期 | 逐项授权和独立状态核对 |

## 对标范围与证据

对比对象的功能来自 2026-11-11 读取的官方文档；“本项目”来自仓库实现和独立运行记录。没有安装 Home Assistant 做同条件性能实验，表中“未在所引资料中确认”仅表示本次检索范围，不能写成产品不具备。

| 路径 | 已有能力/优势 | 选择代价或故障边界 | 与本作品的关系 |
|---|---|---|---|
| Home Assistant Assist + 本地 pipeline [S1,S2] | 本地自然语言、STT/TTS、自动化；可使语音不出本地 | 模型/语言/硬件决定能力与速度；不自动等于任意任务都能完成 | 适合作为未来集成底座和实际基线；本作品当前没有完整语音链 |
| Assist + 本地意图优先 + LLM [S4] | 已支持本地意图先处理，其他交给配置的 AI agent | 能力由本地意图和所选 agent 共同决定 | 规则优先与 LLM 回退已有先例，不能作为原创性依据 |
| Assist + Ollama / OpenAI [S3,S5] | 本地或云端会话模型；通过 exposed entities 限定设备 | 模型工具能力、授权、远程服务和网络依赖需分别配置 | 模型接入和设备授权本身也不是本作品独有 |
| 固定本地模型（部署策略） | 不依赖外部模型服务；模型行为可固定版本 | 有本地常驻内存/算力成本；质量和排队需实测 | 本机量化模型可作候选；可用性和输出正确性分别报告 |
| 固定云端模型（部署策略） | 无需家庭端持有该模型权重；可使用远端服务 | WAN/远端服务故障影响此路径；按实际 token/请求计费 | 目前大模型也在本机，作为云候选代理，不能称实网云验证 |
| RouteLLM 通用模型路由 [S8] | 基于请求选强弱模型，以阈值控制成本/质量；支持多种后端 | 文档基准面向其任务与模型；路由本身也是已有技术 | 未来需以相同任务和预算比较；不复制其节费百分比到本项目 |
| MEC 边缘应用体系 [S7] | 将应用放到网络边缘，提供可授权的网络信息与服务接口 | 平台接入和运营商资源是外部条件 | 提供演进方向，当前家庭 PC 不是已认证 MEC 平台 |
| SenseHome 当前原型 | C 为唯一策略实现，区分 WAN/LAN，读取两端健康/队列/容量，三档能力，动作白名单及事件记录 | 当前设备模拟；本机双模型共享 GPU；没有住户试用或真实空口 | 可检验的场景工程组合；尚未证明较上述平台更快、更准或更便宜 |

## 可发表/答辩的差异化表述

建议表述：“面向存量住宅的多后端控制入口，将 WAN/LAN 与两端模型资源分开观测，以同一 C 策略决定处理位置，并在白名单执行后记录路由原因、失败和能力损失。以配对输入评估网络与算力同时变化时的完成质量与时延。”

这是一项具体场景中的系统组合和证据设计。是否具有性能优势必须由同条件对照回答：固定本地、固定远端、只看网络、联合策略使用相同任务、模型、硬件、故障轨迹与计时边界；模型原始输出、动作正确、保护拒绝和执行状态分别统计。本机远端候选代理的测量不包含外部 WAN 的真实费用与性能。

不得据此表述“首个本地自然语言家居系统”“首创端云路由”“断网仍完成所有任务”“优于 Home Assistant”“节能/节费 X%”“已有客户需求确认”。

## 从业务假设到可验收指标

| 待验证主张 | 客观指标与分母 | 主观/业务补证 | 当前不能推出 |
|---|---|---|---|
| 明确控制在 WAN 故障时可保留 | 指定支持命令中动作正确且模拟状态确认的请求数 / 全部该类请求 | 使用者是否理解控制结果 | 真实灯具已动作、安全认证 |
| 联合路由有用 | 同输入同条件的参考动作正确率、全部请求总时延 p50/p95、模型调用数、失败数 | 操作者能否接受时延/降级 | 全场景最优、生产 SLA |
| 降级说明可理解 | 每次能力损失有事件；用户能复述剩余能力的会话数 / 有效会话数 | 原话、无需提示的复述、恢复操作 | 仅凭日志存在就说体验更好 |
| 能帮助维护 | 盲测正确定位故障层的次数、每次诊断用时 | 集成商实际工单、人员成本 | 减少售后 X%、零维护 |
| 部署可承受 | 实测 RSS/显存、部署步骤完成情况；成本分项未知项可见 | 主机可用性、预算、电价与工时 | 低价网关即可承载任意模型 |

验收目标和用户可接受阈值应在采集前记录；目前没有外部认可的阈值。原型中的工程阈值只是配置，不是客户需求。
