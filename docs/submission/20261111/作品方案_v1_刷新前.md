## 作品简介

家庭智能体接入云端模型后，网络状态成为交互体验的一个变量。本作品面向存量住宅的智能家居集成服务场景，研究如何在广域网劣化或中断时保留控制入口，并明确告知用户哪些能力发生了降级。

系统复用 SenseHome/openvela 原型，将设备端规则、家庭网关本地模型与云端模型组织为三档后端。融合后的纯 C 策略在保持安全/结构化任务本地执行的前提下，对复杂任务联合读取 WAN/LAN 与两端模型健康、队列、并发、内存及可用传输估算，并以可解释代价和恢复迟滞选择后端。服务端健康观测、动作白名单、异常回退和事件记录构成可演示、可回放的闭环。

融合版已完成构建、全量测试和合成实验审计。58,800 条回放记录中，复杂任务的时限内合同完成率为：双端联合84.40%、仅网络62.98%、仅算力61.90%、无迟滞84.52%。联合策略仍有786条未解析请求，不宣称迟滞提高完成率。旧网络策略的四档台架数据单独保留为历史基线。

当前结果来自合成轨迹、固定规划桩、本机桩服务与PC模拟设备，不能代表真实模型准确率或6G空口性能。下一步在既有人工冻结标签上验证真实模型，并补充实网、物理设备与部署成本证据。

# 一、场景概述

## （一）场景名称

**6G链路自适应的家庭AI推理卸载系统**，系统代号 SenseHome。

## （二）场景背景与业务需求来源

需求方画像为中小型智能家居集成服务商：为存量住宅接入照明、窗帘、环境与安防设备，并承担后续运维。其需要控制入口、故障解释和服务恢复机制。对于依赖云端模型的交互路径，广域网中断会使该路径不可用；本地规则、自动化和物理开关是否仍能工作取决于具体产品，不能把个别云端路径的故障扩展成“全部智能家居失效”。

既有原型曾以**开源任务挑战赛道-基于 openvela 智能体的智能家居控制系统**参赛并获**三等奖**（证书编号 CCF-AWRD-ODC-2026-00109）。这支持原型已有开发基础，不能替代本次新增卸载系统的验证，也不等于任何企业已确认需求或参与试点。

本方案尚无具名集成商需求确认函。当前需求证据来自已存在的云端依赖路径、原型使用流程与故障注入验证；下一步需通过集成商访谈确认可接受响应时间、断网保留功能、维护成本和部署条件。正式材料将把行业依据、访谈记录与本项目的直接试点证据分别标注。

## （四）场景摘要

本场景围绕家庭智能体的服务连续性展开。设备端承担规则控制，具备模型运行能力的家庭网关提供本地推理，云端提供可选的远程推理。系统将设备到网关的局域网与网关到云端的广域网分开观测，以保留“广域网断开、局域网仍可用”这一中间状态。

对安全及结构化任务，策略选择本地规则；对复杂自然语言任务，策略根据链路阈值和云端候选算力健康选择云端或网关模型。后端不可用、超时或输出不合规时返回本地规则，事件同时记录原因、耗时和能力损失。选择有后端不等于任务必然完成，接口响应与语义完成必须分别计数。

旧网络策略台架证明了路由、接口回退、错误记录与时延分解能够运行；其中劣化档复杂指令用户总时延为 596.2 毫秒，全网断开时合成复杂任务语义合同完成率为零。融合版另有独立的合成 replay 与 HTTP 网关桩实验，模型耗时和合同结果仍不是真实模型质量或用户体验结论。

6G 关联定位于网络状态可观测和算力协同：未来接入真实网络后，以更稳定的链路预算约束推理位置。当前不声称实现确定性承载或网络切片；落地前需完成真实模型、真实网络与住户需求三类补证。

# 二、场景需求分析

## （一）业务痛点分析

1. **云端路径缺少明确退路。** 当模型服务或 WAN 不可达时，需要保留可执行的本地操作并告知能力损失。
2. **家庭网络存在两段不同的故障边界。** WAN 故障时 LAN 可能仍能承载网关控制；将二者合成一个“在线”开关会丢失这一状态。
3. **控制任务的要求不同。** 结构化控制、复杂语义理解和安全相关操作不应共享无差别的云端路径。
4. **集成商需要能复核的故障解释。** 只显示“失败”不足以区分链路、策略、模型或动作校验问题。
5. **设备端与模型网关的资源不同。** MCU 可承担规则与设备工具；运行本地模型的网关需要另行核算内存、计算与能耗。

## （二）现有方案不足与本方案定位

| 方案 | 已有能力 | 本项目需要补充的验证 |
|---|---|---|
| Home Assistant 等开源平台 | 已支持自动化、自然语言与可选模型接入；不应描述成“不支持自然语言” | 本项目不以替代其能力为创新，考察任务、链路和故障边界下的路由与证据记录 |
| 仅使用云端的模型路径 | 便于集中更新模型 | WAN 或服务异常时，本地回退与恢复是否符合任务要求 |
| 固定本地模型 | 可减少云端依赖 | 实际设备上的模型质量、时延、资源及复杂任务上云需求 |
| 通用模型路由 | 可按质量、成本、难度或负载选模型 | 两段家庭链路、规则保底与任务安全边界的联合验证 |

“端云路由”本身不是新概念。本作品把贡献集中在家庭场景的两段链路、三档能力、C 策略唯一实现和可审计运行证据上。是否优于现有路由方法仍需真实模型和更多基线；当前不宣称算法最优或首创。

# 三、场景方案设计

## （一）总体架构与业务流程

设备端（MCU/模拟器）负责设备工具、规则与本地联锁；家庭网关（当前为 PC）负责观测、C 策略进程、后端调用和事件记录；本地模型运行于有足够资源的网关或边缘主机；云模型通过 HTTP wrapper 接入。MCU、模型网关与云是不同部署角色，不能用设备端目标对象大小代替模型网关内存。

住户提交命令后，网关识别任务类别并从服务端健康缓存构造带来源、观测年龄和序号的链路/算力快照，再交由 `offload_policy.c` 选择配置后端。复杂任务两端资源都参与可用性检查；传输估算只在带宽已知时进入代价，未知保持未知。输出进入 Python schema 和动作白名单检查；后端异常或动作被拒绝时回退本地规则，并记录 `fallback_from`、策略描述、错误、耗时及语义标志。Dashboard 的规则路径更新演示设备状态；远端动作已通过“HTTP 合同桩 → C 策略 → 动作白名单 → PC 模拟 JSON 状态”闭环，仍未接入真实模型或物理设备。原 QEMU 路径的 `command_whitelist.c` 与 Dashboard 的 Python 检查是两个实现，不能描述为同一条已验证的唯一通道。

`offload_policy.c` 是唯一权威策略实现；Python 不复制决策表，只负责可信观测适配、后端调用与记录。Dashboard 的 `/api/command` 进入统一网关，`/api/health` 提供后端状态，JSONL 事件保存策略实现名、决策路径、观测来源与可追溯记录。融合版 C 构建和全量回归已在 r3 完成，审计证据位于 `evidence/network_compute/20261111_fused/`。

## （二）AI+6G 关键技术应用

本方案对应智算网络与算力协同、AI 与通信融合场景。IMT-2030 框架包含 AI 与通信融合方向，可为场景定位提供背景依据，不能替代本系统的网络性能验证。

**网络为 AI 提供决策输入。** 同一复杂请求在云端、本地模型和规则后端之间选择，依据两段链路预算和两端服务健康；传输代价仅在带宽观测可用时计入，避免把未知吞吐伪装成零成本。未来可接入真实 5G/6G 观测接口，比较不同承载条件下可上云比例与用户尾时延。

**任务分级为网络和算力调度提供结构。** 结构化和安全相关任务保留本地路径，复杂理解才参与模型路由，减少不必要的模型上云调用。带宽、能耗与网络侧收益尚未实测。网络切片、确定性承载、无线资源分配和真实空口均未实现，本作品不将端侧隔离包装成独立网络切片。

## （三）资源协同方案

| 资源 | 当前实现 | 边界与待补证 |
|---|---|---|
| 网络 | LAN/WAN 两段建模；TCP 首块延迟与连接级失败注入 | 不模拟分组重传、带宽、切换及完整无线协议栈 |
| 算力 | local/cloud 两端的 model_ready、queue_ms、free_mem_mb、inflight；过期观测闭锁 | 当前来自 HTTP 健康合同桩/模拟轨迹；真实模型队列、显存采集待接入 |
| 策略 | 安全/简单任务固定本地规则；复杂任务比较两端可用性和已知成本，并使用切换裕量/恢复样本 | r3 构建、回归及合成实验审计通过；不宣称策略最优，真实服务效果待补证 |
| 任务 | 安全、结构化、复杂三类 | 分类规则需用真实命令集验证漏判与误判 |
| 数据 | 事件 ID、原因、来源、耗时、异常与能力标志 | 生产日志需脱敏；未采集真实住户数据 |

两端默认约束：模型未就绪、队列 >300 ms、可用内存 <256 MB 或并发 >8 时该候选不可用；若两端均不可用则返回规则路径。阈值和推理/传输估算是演示与测试配置，不是对所有模型通用的容量标准。未知的带宽、队列和内存保持 unknown，不自动转换为零。

## （四）系统组成与部署方案

当前 PC/QEMU 原型复用现有设备工具与 Web 面板。后续设备端可移植 C 规则与设备工具；本地模型必须部署在满足所选模型内存、算力和响应需求的 Linux 主机或边缘盒子，不能直接假设 ESP32/STM32 能运行所选大模型。AutoDL 可用于真实模型接口与实验，但云上两进程不等于真实家庭网关和公网云两地部署。

模型接入采用项目自定义 HTTP JSON wrapper 的 `/infer` 和 `/health` 合同，不直接把其称作 OpenAI API。真实服务接入时需记录模型名、权重版本/哈希、量化、GPU、运行时、并发、上下文长度、温度及接口超时。鉴权、TLS、响应大小限制和运维策略需在生产部署前补齐。

## （三）验证情况

### 1. 方法与口径

旧网络策略的权威完整运行时间为 2026-11-03 03:57:04，结果在 `net_offload/results/results.json`，原件在项目根 `_work/evidence_final/`。每档三类任务各20次、adaptive/static-cloud两臂，共480条原始业务记录。两臂固定网络条件与逐连接采样结果，原始结果可逐条追踪；这不消除宿主调度与TCP噪声。恢复 transition 为随机探索，不宣称配对。融合版策略单独构建和运行，不复用这些旧统计。测试均在单台PC和声明的桩/模拟条件下进行，不能证明广泛网络或用户群体的表现。

### 2. 融合版策略验证（2026-11-11）

r3 完整运行使用当前 C 源码和 Zig 0.17.1 `cc` 前端，`verification.json` 记录全量模式通过、运行期间源码未变化。C 网络策略 70/70、C 算力策略 17/17、net_offload 139 项、Dashboard 37 项、部署 25 项测试均通过；完整 replay、并发、敏感性、安全、HTTP 网关实验及审计也通过。归档目录的 328 个运行文件与验证工作目录逐项 SHA256 一致。

合成 replay 共58,800条记录。`interactive_inference` 中 joint 时限内合同完成率为84.40%（4,254/5,040），network-only为62.98%，compute-only为61.90%，no-hysteresis为84.52%；该指标要求合同完成且总时延不超过配置时限。joint含786条`UNRESOLVED_NO_NLU`。无迟滞臂略高，故不能声称迟滞提高该指标。联合策略在这组指定轨迹中发生93次路由切换，无迟滞臂207次；该计数不等同于业务收益。HTTP网关桩含9,084个请求和持久化事件，679条合同未完成（383条`CONTRACT_NOT_COMPLETED`、296条注入下游`HTTP_503`），所有外层HTTP响应状态均为200。

这些数据来自合成输入、固定规划桩、PC模拟设备和本机桩服务。注入的`HTTP_503`不是实网丢包，合同达标不是NLU准确率；结果不能代表真实GPU、真实6G空口、物理设备或生产环境SLA。详细数字、命令、来源和审计记录见`evidence/network_compute/20261111_fused/README.md`及其子目录。

下节旧网络策略表的用户总时延为 `total_user_ms=probe_ms+policy_ms+backend_ms`，从请求前探测到后端返回结束，未包含真实物理设备动作确认。表中总时延中位数取全部请求，失败快速返回也在其中；只有成功请求参与的 e2e 中位数需单列，不与总口径混用。分段中位数相加不必等于总中位数。融合版 replay 是显式建模时延，HTTP 测试是客户端墙钟时延；三者采用各自记录的口径，不混用。

旧网络策略台架模型后端注入 cloud 300 ms、gateway 150 ms。`semantic_complete` 在台架中由桩合同给出，因此 P1/P2/P3 的语义 100% 只验证记录和回退合同，不代表真实语言理解；P4 复杂语义 0% 是合成 complex 标签的合同结果。台架规则路径是小循环代理，不能代表完整 Dashboard 规则能力；Dashboard 的 `handle_fuzzy_command` 字典可处理“有点冷”等有限模糊表达。真实命令语义必须以真实命令集和模型评测，不能从该合同推导本地规则“完全不理解自然语言”。

### 3. 旧网络策略基线结果

| 档位 | 臂 | 复杂任务后端 | 接口成功 | 语义合同完成 | 用户总时延中位 ms | 探测中位 ms | 后端中位 ms |

| P1 正常 | adaptive | cloud-model | 20/20 | 20/20（桩） | 405.6 | 62.7 | 338.8 |

| P2 劣化 | adaptive | local-model | 20/20 | 20/20（桩） | 596.2 | 425.5 | 169.1 |
| P2 劣化 | static-cloud | cloud-model | 19/20 | 19/20（桩） | 725.6 | 0 | 725.6 |
| P3 WAN 断 | adaptive | local-model | 20/20 | 20/20（桩） | 195.0 | 22.0 | 171.7 |

P2 static-cloud 复杂任务成功请求 e2e 中位数为 727.5 ms；本表统一使用全部请求 total_user 的 725.6 ms。P2 三类任务合计接口成功率为 adaptive 60/60、static-cloud 54/60。P4 三类合计语义合同完成率为 40/60，不能与复杂任务的 0/20 混用。

结果支持的判断是：同步探测让正常档更慢；WAN 劣化时本地后端可抵消一部分成本；WAN 中断而 LAN 可用时仍有模型接口；全断时只能保留规则能力。当前不把结果概括为单一时延倍率，也不宣称全部 KPI 达标或断网仍完成所有自然语言任务。

恢复轨迹共 72 次探测，`probes_to_leave=21`，`probes_to_recover=26`，`probes_after_blackout_to_cloud=15`。前者是首次离云到回云的跨度，后者才是 WAN 恢复后重新上云的次数。本轮按后者满足 ≤15 的边界；尚缺多次重复及秒数上界。

### 4. Dashboard 本地控制补证

独立运行 `evidence/current/dashboard/dashboard_results.json` 使用真实Python Dashboard规则与PC模拟JSON设备状态，四档每类20次，共160请求。开关灯p50为3.066—3.783 ms、p95最大4.434 ms；只读安防状态查询p50为1.242—1.427 ms、p95最大1.711 ms，模拟状态/查询结果160次均确认。该范围验证本地路径绕过同步探测；不是硬件闭环或任意安全动作承诺。燃气与门禁等未授权命令应返回拒绝，不执行危险动作。

### 5. 可复核证据

`build.ps1` 编译 C 程序并运行测试，输出编译器/Python/OS/commit 与二进制哈希；`run_evidence.ps1` 运行台架并验证结果 schema。提交时保留完整运行目录、配对 trace、原始事件及桩参数。`results/runs/run_A~F.json` 为历史记录，只用于版本追溯，不再作为当前 KPI 依据。

### 6. 尚待验证

真实模型语义、真实控制动作确认、外部链路下的p95/p99与阈值敏感性、更多独立网络轨迹、网关内存/能耗/成本与真实设备并发均需补测。r3已有合成/桩条件下的尾时延统计和12个单因素敏感性变体，不能代替上述外部验证。当前动作白名单测试证明特定危险输出被拒绝，不能推导所有 prompt injection 或物理风险已被消除。

## （四）与现有系统的兼容性

项目保留原设备工具和控制函数，以注入式规则后端衔接网关。策略库为纯 C，便于移植；完整 PC 网关还依赖 Python、子进程与 HTTP，目标 RTOS 移植需重新适配网络、计时、IPC 和设备 API，不能承诺直接固件更新即可兼容所有网关。协议、资源与安全验收应逐平台完成。

# 五、产业价值与推广

## （一）应用效果量化

现阶段价值是把服务连续性分成可观察的层级：接口可用、语义合同、动作执行与物理确认分别计量。台架量化了正常档的额外探测成本和劣化档的回退收益，为选择部署主机、模型和网络预算提供依据。它还没有形成住户体验改善、真实成本节省或商业收益结论。

## （二）可复制可推广性

C 策略、HTTP 合同、配对 trace 和构建清单使第三方可在普通 PC 上复核设计。推广对象优先是已有可运行模型的家庭网关或边缘主机；设备 MCU 继续承担规则与工具。每次迁移重新记录模型、设备、网络及安全约束，不能将 PC 台架结果直接复制为目标硬件承诺。

## （三）产业带动与经济效益

拟为集成服务商提供网关适配、部署工具和故障追溯能力。定价、订阅或服务模式尚未验证，应以真实需求确认、部署成本和运维工时测量后再建立测算。当前不采用未经核验的市场规模、物料报价或收益数字作为价值证据。
