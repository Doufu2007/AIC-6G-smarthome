# 真实模型与受控HTTP代理独立审查

结论：本次只读审查范围内未发现未解决的Critical或Important项。120行主矩阵、102次实际模型POST和18次未转发代理503，与原始行、代理trace及摘要一致。结论限于明确的软件故障/代理等待条件，不能改写为真实WAN、GPU拥塞、独立云边或6G空口收益。

## 审查方式

独立读取`docs/deployment/real_fault_eval_v2.py`、注册文件、五个条件的原始报告/JSONL/代理日志、摘要、作者audit及`verify_run.py`。没有运行推理、重启服务、改变配置、修改原始记录或重写作者audit。另用独立离线检查代码复算全部120行评分和关键计数；机器结果保存于`2026-11-11-real-fault-v2-independent-counts.json`。

没有直接执行作者`verify_run.py`，因为该脚本会重新写`audit.json`；仅审查其代码并以独立计算核验。原报告添加的代理计数字段之外，全部继承行字段与`report.gateway_raw.json`逐项相同。

预热单列：五条件各两次代理POST，共10次；其中8次实际转发模型、2次代理503，和主矩阵trace没有交集。条件内另有60次模型清单GET和60次代理telemetry GET；启动时额外两个直接模型清单探测不在这个条件内计数。所有这些计数都不当作正确完成任务数。

抽查失败：`cloud_http503/C01/fixed-cloud`与`local_http503/C01/network-only`原始代理返回503；adapter/网关错误记录为HTTP_502并进入fallback，网关`interface_ok=True`仍被评分为`task_completed=False`。这是接口响应与业务完成分离的实际例子，没有用快速失败的约5ms冒充成功时延优势。

## 条件、配对和状态

- 每条件6个配对块，每块恰有四臂；命令、输入哈希、初始模拟状态、参考动作和观测哈希相同，轮换顺序与blocks原始记录一致。
- 原始JSONL与report内行一致；当前冻结scorer对120行重算与保存评分一致，摘要复算亦一致。无运行器失败或跳过被隐藏。
- `run_registered`每个条件分别调用冻结`evaluate`，后者建立新的四个C策略子进程并在finally关闭。各条件、各臂首个`decision_sequence`均为1，支持条件之间独立策略历史；条件内相同臂的历史连续。没有延用旧注入矩阵跨条件的恢复迟滞状态。
- 503条件的模型清单路径仍转发可用，网络可达；代理健康接口同时将ready报false。实际POST503记录与该设置相符。底层模型进程并未真的退出。

## 700ms等待的真实含义

代理在POST转发前执行`threading.Event().wait(delay_ms / 1000)`，用`perf_counter`测实际等待，随后才向真实模型发送请求。含预热的测量范围为：

| 延迟位置 | 代理等待最小/最大 |
|---|---:|
| 第二端代理 | 701.068 / 714.228 ms |
| 本地端代理 | 700.899 / 714.735 ms |

健康接口中的`queue_ms`来自上一次实际测得的固定代理准入等待，并保存样本年龄；它是恒定条件下保持的样本，不是GPU队列长度、GPU忙时、当前排队预测或真实WAN拥塞。代码、注册与summary.md均声明该范围。实验可以支持“读取该代理观测后避开已设置慢/失败候选”的条件性行为，不能支持任意负载预测或生产网络可靠性。
