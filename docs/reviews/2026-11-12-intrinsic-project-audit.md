# 项目自身功能与可靠性审计（2026-11-12）

本次只检查项目实现、能力边界和运行行为，不以文稿、访谈、成本记录或提交手续作为问题。审计未修改生产源码，未重跑真实模型；使用隔离状态、注入计划、虚拟时钟和自有 loopback 服务。原 offload_events.jsonl SHA256 仍为 `f8871ff4c70a5c03e5fbd7e6fc32ea224a61c6cae34279545c674ae3da3abc54`。既有 v1—v4 封版文件未覆盖。

P1 表示应优先处理的正确性或可用性问题；P2 表示功能完整性或工程能力缺口。它们是工程修复优先级，不能换算为赛事分数。

## F01 / P1：合法动作执行完，不等于用户任务完成

- 已隔离复现：用户要求“把客厅灯光设为60%，再把卧室灯光设为30%”，注入合法错误计划“仅把客厅设为10%”。计划校验通过，网关最终 `semantic_complete=True`，实际状态客厅10%、卧室0%。
- 根因：`openai_backend.py` 的命令合同约束动作白名单、字段范围、房间和关键字，但没有充分校验原始任务的全部目标和数值。`device_actions.py:58` 将整批合法动作执行成功直接标记为语义完成，`offload_gateway.py:649` 采用该值。MQTT 回执层 `durable_receipts.py:101` 也主要根据计划已应用判定完成，并没有补足用户目标验收。
- 影响：漏房间、漏步骤、错目标值仍可能被报告为任务完成。
- 修复：建立服务端请求目标合同，先检查计划对明确目标的覆盖、方向和数值，再按实际观测验收全部目标。拆分计划合法、动作执行完成、用户目标完成；无法可靠提取目标时澄清，不能默认完成。
- 验收：漏动作、错房间、错值、部分执行、状态未知均不得获得 `task_complete=true`；正确计划全部达标才完成。
- 边界：这是注入合法错计划的验证缺口，不能解释为真实模型已在这个命令上犯错，也不能推导错误率。
- 证据：`_work/intrinsic_audit/planning/result.json` 的 `target_acceptance`。

## F02 / P1：规则分流存在不能升级的理解死路

- 已隔离复现：“把卧室灯调亮一点”被分类为 simple，强制选择 local-rules，明确规则解析失败，结果“暂不理解”，可用模型调用次数为0。
- 根因：`offload_gateway.py:424` 按关键字判简单任务，`:491` 强制规则；`bridge_server.py:547` 的明确计划解析器并不支持该表达。两者能力边界不一致。
- 修复：规则仅在完整解析成功时接管；未解析返回 UNRESOLVED，并进入模型或澄清流程。相对调整需要可信当前值和明确调整幅度，不能自行猜数值。
- 验收：常见表达及同义改写不会被错误困在规则层；存在歧义时可继续澄清。
- 证据：planning/result.json 的 `rule_dead_end`。

## F03 / P1：缺少真正的多轮澄清续接

- 已隔离复现：连续调用“有点暗”→“卧室”，进入网关的两轮 context 均为 `{}`。只有“卧室”不能恢复前一轮操作目标；即便手动给“再亮一点”传房间 context，模型动作校验仍要求位置出现在当轮文本而拒绝。
- 根因：`web_panel.html:331` 只提交本轮 command；`bridge_server.py:1013` 无待补槽位状态；`openai_backend.py:316` 不接受可信会话目标。
- 修复：加入会话隔离、待澄清意图、缺失槽位、过期和取消机制。由服务器合并可信上下文后统一校验，禁止让模型自行决定上下文是否可信。
- 验收：“有点暗→卧室→调到60%”能够安全续接；不同会话互不继承，过期与取消后不执行旧意图。
- 证据：planning/result.json 的 `clarification_state`。

## F04 / P1：一条慢请求阻塞整个 HTTP 入口

- 已隔离复现：使用实际 `make_isolated_server()`，命令处理被短暂阻塞时，另一个 /api/health 请求无法完成；解除命令阻塞后两者正常返回。
- 根因：`docs/trial_v2/run_isolated_gateway.py:110` 使用单线程 HTTPServer；v3/v4 正式本机入口复用该服务器。原 bridge 主入口也使用 HTTPServer。推理、执行等待与状态接口占用同一处理线程。
- 影响：慢模型请求会连带阻塞状态、健康和其他控制请求。
- 修复：有界并发/任务队列与非阻塞查询，设备写入保留序列化；对共享 C 策略进程、后端记录和持久层同步一并检查，不能只把 HTTPServer 改为线程服务器。
- 验收：长规划期间健康与状态查询仍响应，独立控制不被无界阻塞，设备动作顺序和幂等不退化。
- 证据：`_work/intrinsic_audit/root_probe_result.json` 的 `http`。

## F05 / P1：慢故障耗尽恢复启动预算，且缺少端到端 deadline

- 配置：`docs/demo_v3/run_live.py:139` 后端超时15秒，`:147` 备用启动预算10秒。
- 已用虚拟时钟复现：首端15秒超时后，即使备用健康且可在0.1秒完成，也因预算耗尽完全不调用备用。另一用例首端1秒失败、备用耗时15秒，整体16秒，超过10秒。
- 根因：`planning_recovery.py:159` 同步等待首端，`:188` 才判断预算，`:211` 启动备用后不约束剩余总预算。代码明确定义为 secondary-launch-only；这不是总请求超时。
- 修复：统一端到端 deadline，明确切分首端、健康检查、备用和执行预算；向下传递剩余时间，在规划提交前处理取消与过期，不因模型迟到提交过时动作。
- 验收：快速失败与慢超时均有规定的备用窗口；超出总期限不会继续提交新动作；已提交动作通过命令ID回查。
- 证据：root_probe_result.json 的 `slow_failure`、`secondary_long_call`。这两项是确定性控制流验证，非真实模型耗时测量。

## F06 / P1：MQTT 短暂断开后原适配器无法恢复

- 已使用私有 broker 和软件实体复现：初始查询成功；broker正常停止再在原端口重启后，旧 transport 查询返回 null，新 transport 查询成功。
- 根因：`mqtt_receipts.py:132` 禁用 reconnect_on_failure，未提供显式连接恢复流程。
- 修复：恢复连接和重新订阅，保留持久命令ID；对已提交但状态未知的命令只回查，不因重连重发动作。连接恢复与动作重发应分别控制。
- 验收：broker中断后恢复可查询和提交；旧 unknown 命令不重复执行。
- 证据：`_work/intrinsic_audit/execution/reconnect_result.json`，相关自有进程已停止。

## F07 / P1：查询失败后旧状态缺少过期标记

- 已隔离复现：snapshot失败后，旧状态与 `scope=current-software-platform-observation` 原样保留。
- 根因：`bridge_server.py:661` 查询失败直接返回None，`:1072` 的 /api/state 仍返回旧缓存；`:699` 未存最后成功观测时间、新鲜度和连接状态。
- 影响：页面可能继续展示断连前的灯光或窗帘状态，用户无法判断其是否仍可信。
- 修复：分开保留最后观测值、观测时间、数据年龄、stale/unknown和连接状态；查询失败不伪装为当前观测。
- 验收：断连和过期时状态明确显示最后成功时间及未知，恢复后更新；历史回执仍不能充当当前状态。
- 证据：execution/probe.py；代理已完成隔离复现，原始结果另存 execution/probe_result.json。

## F08 / P2：页面没有把幂等命令ID与回查接成完整流程

- 已静态确认：`web_panel.html:331` 每次只发送command，无稳定客户端command_id，无pending持久化，无receipt查询；`durable_receipts.py:131` 无ID时每次生成UUID。
- 影响：HTTP响应丢失后，页面无法自动回查这一次请求；用户再次发送会成为新命令，底层同ID去重不能识别它属于同一次重试。当前页面没有自动重试，不能写成已经发生自动重复执行。
- 修复：先持久化客户端请求ID，首次与重试保持同ID；查询请求状态后由用户明确选择新意图。ID必须在规划前绑定原始请求，避免重规划后相同ID不同计划产生冲突。
- 验收：响应丢失、刷新、重复点击和重启恢复都有确定结果，不重复提交同一意图。

## F09 / P2：正式执行模式存在功能断口

- 已确认：MQTT模式“离家模式”返回 `LEGACY_SCENE_NOT_ADAPTED_TO_MQTT_RECEIPTS`，主动巡检返回 `PATROL_NOT_ADAPTED_TO_MQTT_RECEIPTS`，没有执行。
- 入口区别：当前 v4 复用隔离服务器，/api/patrol/trigger 不在允许列表，直接404；原 bridge 入口允许该路由，却仍将未适配报告包为status=ok，旧页面只查数组而可能显示巡检完成。不能把原bridge的伪完成路径说成v4已实测成功触发。
- 修复：场景和巡检生成受约束计划，统一进入命令ID、执行、回执和状态验收；能力未接通前明确显示不可用。
- 验收：不同入口使用同一能力表，页面承诺与实际可执行能力一致；完整执行仍经过统一保护。

## F11 / 能力限制：当前调度尚不能充分适应实际排队与任务耗时

- 已静态确认：`docs/deployment/fused_eval.py:160` 实际模型后端queue/inflight未观测；`bridge_server.py:952` 带宽为未知；C策略 `offload_policy.c:441` 使用固定推理代价。当前v4默认由冻结结果选择local-first。
- 影响：策略代码有资源接口，但当前运行路径缺少足够的在线输入和按任务更新的代价估计，因此无法充分根据真实GPU排队、任务长短和链路变化做联合选择。
- 修复：先在真实可测服务中补请求排队/在途、推理和传输分解，建立分任务在线代价与不确定性处理；在确有资源竞争时验证joint相对简单策略的价值，结果不支持就继续以简单策略作为默认。
- 6G关联：现有软件闭环可面向未来网络演进，但没有实际6G测量；关键工程缺口是可观测资源和自适应闭环，而不是把网络名称换成6G。

## 推荐修复顺序

1. F01目标验收：首先防止做错仍报完成。
2. F02/F03理解与澄清：让常见表达形成可完成的请求。
3. F04/F05可用性与时限：避免慢请求拖住全系统，并明确恢复窗口。
4. F06/F07/F08/F10：补平台断连、状态新鲜度、客户端幂等与完整重启。
5. F09统一能力、F11在线资源调度：补完整业务闭环，再验证调度是否带来实际收益。

既有通过的定向测试证明了已覆盖的路径；本次用例揭示的是先前未充分覆盖的用户目标、输入分流和生命周期路径。本报告不将这些发现解释为已经修复，也不将工程测试结果换算为获奖概率。
