**项目本体第二轮审计，2026-11-12**

当前项目仍存在可复现的软件缺陷，也存在自然语言理解、质量感知调度和部署能力的限制。上一轮回归通过只证明已覆盖用例通过。本轮使用当前源码进一步探测边界，没有修改生产实现。

本轮隔离探针分三种：真实源码与私有 SQLite 软件实体/回执/请求库；正式 loopback HTTP wrapper 与受控无副作用处理器；模型输出夹具与在线计数器。没有重新运行真实模型，没有连接实体硬件或 AutoDL，没有测量 6G 链路。模型实际行为引用 v5 三轮烟测，并明确保留版本和样本边界。原状态与事件文件及上一轮报告列出的 22 项源码/保护文件哈希全部匹配，见 `_work/intrinsic_audit_v6/source_preservation.json`。

**各项如何修，以及修好应达到什么条件**

1. V6-01：把平台快照查询时间与每个传感器的实际采样时间分开。传感器要带来源、序列、完整时间戳、有效状态和有效期；缺少可信新采样时只能报告未知，不可自动控制。被冻结的初始化值必须标成演示/未采样，不因读取数据库而续期。逐房间报告缺测项。关灯策略还应区分“没有检测到运动”与“确认无人”，加入持续时间和用户手动控制保护。验收：旧值、缺时间、来源无效均不改灯帘；新鲜且符合明确策略的观测才允许动作。

2. V6-02：把“存在未支持能力”与“已接入目标尚待观测”独立存储。灯帘applied但未确认时保持可回查；确认后supported_scope_complete=true，安防仍未支持，所以整体task_complete继续false。验收：首次失联后恢复回查能确认支持部分，且不再次提交动作、不虚报安防完成。

3. V6-03：请求结果增加revision，在事务中比较读取版本后更新；结合观测版本/时间合并。旧回查或缺失观测不能推翻较新的已确认结果。历史完成事实与后来设备状态变化应分字段表示，不能简单混用一个布尔值。验收：用两个可控并发回查穷举成功/超时返回顺序，持久记录不因旧结果倒退。

4. V6-04：把durable receipt作为执行事实源。拿到applied后，任何状态缓存错误都保留command_id、receipt、actions和execution_state，将验收记为observation_pending并单列cache_error。普通异常退出也应核查是否已经预留/提交，不能直接当作提交前失败。验收：缓存不可写、短暂文件占用和回查失败均可在恢复后对账；原ID仅提交一次。

5. V6-05：为入站请求头和请求体设置各自的绝对读取期限与大小限制，超期关闭socket释放worker。读取期限与后面的规划/提交期限分开，避免看门狗误杀已进入执行阶段的请求。验收：持续滴字节也在总期限内释放槽位，正常健康/状态请求恢复，不依靠客户端主动关闭。

6. V6-06：命令与巡检共用context对象校验，在dict转换及账本调用前拒绝非对象，返回400 INVALID_CONTEXT。验收：三类畸形值稳定返回JSON错误，不进入巡检或持久化，不以宽泛吞异常替代输入验证。

7. V6-07：快照入口校验sensors容器及每房间结构、类型、数值范围和来源/采样信息。单房间坏数据按未知隔离，阻止相关自动控制。验收：null、数组、字符串、非有限值和部分房间缺测不会让巡检崩溃或被报成全部可用。

**其他入口或降级模式的已复现问题**

这些也属于项目代码问题，但不应冒充当前v4正式接口的漏洞：

- 本地无MQTT状态路径：`load_state()`捕获所有读/解析异常后静默生成默认值。隔离损坏JSON后，下一次开灯任务报告成功并覆盖损坏文件，丢失原状态及故障证据。应区分首次创建与已有文件损坏，保留坏文件、显式降级/恢复；有权威MQTT实体时也应由实体恢复，不凭空重置设备状态。
- 基础脚本的后台巡检生命周期：单次异常退出后patrol_running仍true；共享布尔值控制旧循环，新旧线程在off→on之后均能继续巡检。应使用每次启动独立的stop Event、线程句柄、单实例锁和finally状态清理。**正式v4 wrapper当前禁用了toggle路由且没有自动启动该循环**，因此这两项是备用入口/未来接入的缺陷，不列入当前正式HTTP路径的主要问题。
